## 3. บันทึกผลการตัดสินใจ (8 นาที, ทำร่วมกัน)

**ADR ที่รีวิว:** `docs/adr/0002-publish-orderplaced-event-to-rabbitmq.md` (เอกสารที่สถาปนิกส่งให้ใช้ในการประชุมจริง) โดย Kitkanaporn Umpaimungkorn
**AI review ที่ใช้ในการประชุม:** `exercise/outputs/3-review.md` (เอกสารจาก AI analyst ที่ใช้ในการประชุมจริง; Claude Code · Claude Opus 5.5)
**สมาชิกและบทบาท:** Kitkanaporn Umpaimungkorn (สถาปนิกและ AI analyst), Chayakorn Chaiyaphan (Product Owner), Nasapon Pitoonmanit (SRE)

**มติคณะกรรมการ:** **อนุมัติโดยมีเงื่อนไข** ทั้ง PO และ SRE เห็นด้วยกับแนวทาง RabbitMQ + outbox แต่ต้องแก้และปิดประเด็นตามรายการด้านล่างก่อนใช้งานจริง

**สรุปในมุมของสถาปนิก:** ฉันยอมรับว่า ADR ยังไม่พร้อมใช้งานจริง จุดที่หนักที่สุดคือ outbox ที่ฉันเพิ่มเข้าไปเองยังออกแบบไม่ครบ เพราะ checkoutservice ไม่มี DB เก็บ order และการชาร์จเงินอยู่นอก transaction ส่วนเรื่อง SLA ของอีเมล (จาก PO) และเรื่องการดูแลระบบ/on-call (จาก SRE) เป็นข้อมูลที่ฉันไม่มีตอนเขียน ADR ต้องได้คำตอบจากเจ้าของเรื่องก่อนถึงจะปิด Open questions ได้

**สรุปในมุมของ AI analyst:** จากข้อกังวลทั้งหมด 8 ข้อ ผลรีวิวของ AI มีเต็ม ๆ 4 ข้อ (แถว 1, 2, 4, 6) มีบางส่วน 3 ข้อ (แถว 3, 5, 7: AI ชี้ว่ามีช่องว่าง แต่ไม่รู้ว่าธุรกิจหรือทีม ops ยอมรับได้แค่ไหน) และไม่มีเลย 1 ข้อ (แถว 8: emailservice เป็น Python ซึ่งต้องดูซอร์สโค้ด) AI เก่งเรื่องหาความขัดแย้งในเอกสารและคำนวณตัวเลข แต่ตอบเรื่องที่ต้องใช้ข้อมูลนอกเอกสารไม่ได้

**สิ่งที่สถาปนิกต้องแก้ใน ADR (ตามมติ):**
1. **Outbox (ร่วมกับ SRE):** ระบุว่าจะเก็บ event ที่ไหน เขียนหลังชาร์จเงินและส่งของสำเร็จ และถ้าเขียนไม่สำเร็จจะ retry หรือ reconcile อย่างไร เพิ่ม PostgreSQL กับ relay ใน diagram และใส่ในแผน fault injection กับ latency budget
2. **Email backlog (ร่วมกับ PO):** รอ PO ตกลง SLA อีเมลกับ Marketing และระยะเวลาพีก แล้วใส่ตัวเลขใน ADR (ที่ 200/s เข้า 50/s ออก จะค้างประมาณ 540,000 ฉบับต่อพีก 1 ชั่วโมง ใช้ราว 3 ชั่วโมงระบาย) และระบุ global rate limiter 50/s ที่คุมทุก replica
3. **Loyalty ภายใน 1 นาที (ร่วมกับ SRE):** วัด lag ตั้งแต่ outbox → relay → queue → consumer เพิ่ม alert ที่ครอบคลุม outbox age และเขียนขั้นตอน replay/reconcile ของ DLQ
4. **emailservice:** ตัดสินใจว่าจะเขียน consumer ด้วย Python ต่อ หรือย้ายเป็น Go โดยดูภาระของทีมที่ถนัด Go
5. **RabbitMQ (ร่วมกับ SRE):** ยืนยัน topology/HA, backup/restore และเจ้าของ on-call แทนข้อที่ ADR ระบุไว้เป็น [Inferred]

**ใครยกประเด็นใด** ระบุทุกข้อกังวลที่คณะกรรมการอภิปราย

| # | ข้อกังวล | ผู้ยกประเด็น (ผลรีวิว AI / สถาปนิก / PO / SRE / security) | อยู่ในผลรีวิวของ AI หรือไม่ | AI มีทางรู้ได้หรือไม่ เพราะเหตุใด |
|---|---|---|---|---|
| 1 | ADR ระบุว่า checkoutservice ยังไม่มี data store และไม่ได้ระบุ order record แต่เสนอ transaction เดียวกับการสร้าง order; จึงยังไม่ชัดว่าจะ persist order/outbox ร่วมกันอย่างไร โดยเฉพาะเมื่อ DB write ล้มหลัง charge/ship | ผลรีวิว AI | มี | รู้ได้จากการเทียบข้อเท็จจริงเรื่องไม่มี data store กับการอ้าง transaction ร่วมใน ADR; เป็นความไม่สอดคล้องในหลักฐานที่ให้มา |

**ข้อค้นพบที่ดีที่สุดของ AI** (ที่มนุษย์มองข้ามไป): จับได้ว่า ADR ขัดกันเอง คือบอกว่า checkoutservice ไม่มี data store แต่เสนอให้เขียน outbox ใน transaction เดียวกับการสร้าง order ทั้งที่ฉันเป็นคนเขียนส่วนนี้เองแต่มองไม่เห็น
**ข้อค้นพบที่อ่อนที่สุดของ AI** (กว้างเกินไป ผิด หรือไม่เกี่ยวข้อง): ข้อเสนอให้ลอง publish ตรงไป RabbitMQ โดยไม่มี outbox แล้ว "วัดว่า event loss ยอมรับได้แค่ไหน" ไม่ตรงกับ R-12 ที่ต้องให้แต้มทุก order ครั้งเดียว ทางเลือกนี้จึงแทบตัดทิ้งได้ตั้งแต่แรก
